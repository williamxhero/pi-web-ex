# Pi Web Ex 品牌、版本与更新设计

## 目标与边界

让用户在界面、安装和更新过程中能明确辨认 Pi Web Ex，且不会被更新到上游 Pi Web。GitHub 库名已经是 [`williamxhero/pi-web-ex`](https://github.com/williamxhero/pi-web-ex)。本次做法基于已合入上游 `0.19.0` 的 fork；不改 `pi-web` 命令、环境变量名、已有用户数据和配置，不部署、不推送 tag、不发布首个 Release。发布动作需另行明确授权。

## 品牌显示

- 正式名 `Pi Web Ex` 用于应用与公开演示的浏览器标题、PWA、登录、首页、离线页和界面文案；命令行的产品文案同样用 Ex。窄侧栏显示 `πx`，有空间时显示 `Pi Web Ex`；沿用侧栏现有适配机制，不加宽最窄 180 px 的侧栏，不隐藏新建、搜索、排序等按钮来腾位置。
- 点击字标打开独立的小卡片，不把版本塞回工具栏。键盘、鼠标和触屏均可打开，支持 Escape 关闭；卡片显示 `Pi Web Ex`、完整的 `0.19.0+1.0.0` 和单独标注的 `Pi SDK 1.6.1`。产品名、完整版本与 SDK 版本读屏可辨。主应用和公开演示使用相同规则。
- 参考 [CPA-Manager-Plus-ex](https://github.com/williamxhero/CPA-Manager-Plus-ex) 的右下角斜体 `Ex` 徽标，保留原 π 图形，更新 favicon、PWA/Apple 图标、新建/登录/离线页、通知与未读 tab 图标底图、演示资源。徽标在大尺寸可读；为 16 px 输出设计可辨识的小尺寸取样，不用一份大图机械缩放全部尺寸。第三方图标与历史截图不是产品 logo，不改。

## 版本

- 保留根 `package.json` 的 `version` 作为上游版本输入（随上游合并更新），叉库独立版本初始为 `1.0.0`，放在单独的受跟踪、可打包的版本文件中。对外产品版本由两者生成，不另维护第 3 份字符串。有效格式为 `X.Y.Z+A.B.C`；比较时先逐段比上游，再逐段比 fork，不能把 `+` 后部分当作 SemVer 的可忽略元数据。坏格式、预发布和低版本不作为升级候选。
- CLI `--version`、网页版本卡/首页、PWA 缓存标识、更新提示、发行标题与说明、下载展示均使用完整组合号。Pi SDK、第三方插件和 Node.js 的各自版本不是产品版本，保持原语义。Docker tag 不支持 `+`，机器可用标签取明确的 `0.19.0-ex.1.0.0`；显示仍用 `0.19.0+1.0.0`。发布脚本必须用组合号校验 `v0.19.0+1.0.0` tag；不能保留会错误递增上游字段的 `npm version patch` fork 发布入口。

## 选择的分发和更新方式

**选用 Ex GitHub Releases 作为唯一查询和下载渠道。** 另外两种做法未选：复用上游 npm 渠道会覆盖 fork；建一个新的 npm 更新渠道则需要首发与 npm Trusted Publishing，且 npm 版本排序不把 `+` 后的 fork 号作为更新顺序；采用它还需额外维护内部发布序号。GitHub Release 的标签和资产可以同时表达两个版本，不需要双渠道对账。

- 使用 Ex 仓库的 stable Release（不是可能指向同步上游提交的 Git tag 或 npm dist-tag）。发布流程先把已构建的 npm 安装包上传为草稿 Release 中命名固定的资产 `pi-web-ex.tgz`，验证资产及 Ex 容器镜像均可用后才公开发行；用户仍通过 npm 安装 tarball，但不依赖 npm registry 中已经存在某个 Ex 包。包名/锁文件根元数据改为 `@williamxhero/pi-web-ex`，CLI 名仍是 `pi-web`。源码版本输入与发行包清单分开：打包时在暂存副本的 npm 清单写入完整组合号，并保留单独的上游版本输入，以免安装后的 CLI 重复拼接。发布验收用独立 npm prefix 离线实测 `npm pack`、全局安装和同上游不同 fork 版本的覆盖，确保 npm 不会因 SemVer 排序忽略 `+` 而误报没更新（已先用最小占位 npm 包验证 `0.19.0+1.0.0` → `0.19.0+1.0.1` 会替换文件和清单；实际 Ex 包仍需验收）。构建包必须带 Ex 品牌资源、版本文件和可启动的 Next 产物；现有 npm 包管理机制仍解析其依赖。工作流只能在 Ex 仓库的精确组合号 tag 发布，生成自己的 GHCR 镜像；未获授权，本次只改工作流和验证打包契约。
- CLI 与 API 共用 Release 来源、组合号校验与比较。仅接受 Ex 仓库自己的 tag 和指定资产；安装 URL 从确认的 Ex owner/repo、有效 tag 和固定资产名生成，不将 Release 文本提供的任意 URL 交给安装器。拒绝草稿、预发布及格式错误；查不到 Release 时明确「尚无 Ex 发布」，已有 Release 但缺安装资产时说明不可安装，不装上游，也不误报已是最新。暂时失败按检查失败处理，不当作新版本。
- 网页只自动检查并提供 Ex Release 详情链接，绝不执行安装；继续尊重 `PI_OFFLINE` 和 `PI_WEB_SKIP_VERSION_CHECK`。`pi-web update --check` 只检查；`pi-web update` 由用户启动，只在确认有更新、全局安装属于 Ex 且无运行中实例时安装该 Ex 资产；保留 npx/源码/容器路径的手动提示，不就地替换这些安装。Windows CLI 及其子进程保持无窗口、非交互，退出结果对调用者可见。旧的 `@agegr/pi-web` 全局安装或以旧包名打包的 fork 不做静默迁移；文档说明如何先停旧实例，再显式切换到 Ex，同时保留原用户数据。

## 仓库链接和 README

所有指向本产品的链接和地址切到 Ex：包元数据、CLI 提示、网页与演示、Release/资产/镜像、问题反馈、CI 与文档中的命令。仅保留明确说明来源历史的上游链接和合并用 Git remote，以及真正的独立外部依赖链接（Pi SDK 等）；它们不是 Ex 下载/反馈入口。产品安装文档不得继续指向上游发布件。

根 README 采用 CPA 风格：右上角独立 `Ex` 徽标，开头说明产品与版本，快速开始（源码立即可用；Release 安装说明如实标注首发前状态），接着列 fork 功能及入口。上游原版说明独立在归档文档中，明确不是 Ex 安装入口；如需从公开文档链接过去，链接使用 fork 内的文档。尚未启用的 GitHub Pages 和不存在的 Release 不当作已经上线的入口。重大功能交付时，从当前全部 fork 能力重选三项 GitHub About 文案；README 先改，随后同步 About 并回读，不宣称尚未发布的功能已发布。

## 验收

- 最窄/宽侧栏的实际浏览器布局与字标卡片；默认/覆盖 PWA 名，检查 favicon/PWA/离线图标及实际资源输出，主站与公开演示一致。
- `pi-web --version` 显示完整组合号；比较测试覆盖同上游不同 fork、不同上游、相等、坏格式。模拟 Ex Releases：没有 Release、缺资产、非稳定版本、网络失败、成功检查；验证网页不安装，CLI check 不安装，手动只使用 Ex 资产且运行中实例受保护。校验同一 `pi-web` 命令和旧安装路径不会被回写到上游。
- 检查构建配置、发布标签、安装资产路径、镜像标签、文档与所有一方地址；自动核对更新执行链中无上游发布端点。授权发布前只在隔离环境验证，不执行真实发布。按改动范围跑定向测试、TypeScript 和 lint；若实际触及公共模块到无法可靠划定范围或有明确门禁，再按仓库规则集中跑全量。
